Progress So Far

Since the proposal, we have brought up the dual-core PSoC 6, implemented integer FIR filtering with runtime-supplied coefficients, and profiled scalar and DSP/unrolled kernels. A FIR job filters an independent block with zero initial history; its tap count is the number of coefficients used per output. Infineon supplies startup, timer, and IPC (inter-processor communication) drivers. The filtering kernels, job ownership protocol, and batch execution are our own implementations.

We first implemented and verified an FIR filtering kernel on each core and measured its execution time, then implemented a single-job cross-core handoff and a naive concurrent baseline. Both cores claim the next unclaimed job, release the hardware IPC lock, and execute separate filtering jobs concurrently. Full-output checks, completion counts, guards, and separate timing traces validate execution. The runtime supports up to 32 preloaded FIR jobs in 16 KiB of shared storage. Threshold operations, general enqueueing, dependencies, profiled static assignment, and work stealing remain planned areas of exploration.

Preliminary Results

Experimental Setup

With Arm GCC 14.2.1 (-O2), we measure 31 trials per workload, mode, and clock setting after three warmups. Scalar and DSP/unrolled variants are tested on each core; choices are fixed before parallel trials. The assignment rule itself uses no cost estimates. A common on-board TCPWM counter measures elapsed time using its configured frequency. We evaluated two clock configurations: M4 at 150 MHz which required M0+ to be at 75 MHz, and both cores at 100 MHz.

The M4-only reference makes direct filter calls over the same shared buffers, without work queue locks or worker wakeup. Parallel timing includes ready-list initialization, publication, IPC wakeup, claiming, execution, and completion waiting. Input/plan preparation and correctness checks are outside both timers. Per-job timestamps are enabled only in separate diagnostic batches.

Across 25 workloads, the 150-MHz M4 and 75-MHz M0+ configuration of the greedy scheduler beat the fastest tested M4-only configuration (150 MHz) in only 2 cases, with a best median speedup of approximately 1.10×. With both cores at 100 MHz, it beat M4-only at 100 MHz in 19 cases. Separate traces confirmed kernel overlap in all 50 traced batches. Across both accepted clock sweeps, 8560 batches and 139,668 job executions passed checks, including warmups and calibration. The earlier single-slot NOOP handoff measured about 5.88 µs round trip at 150/75 MHz.

Challenges and Remaining Unknowns

Initial bring-up required hardware UART-path diagnosis and a TX/RX jumper cable workaround, intended to ease debugging later on; this unforeseen issue led to delays. The measurements included in this report use KitProg debugger extraction rather than prints after execution, so timing does not depend on serial output. Earlier large-block tests also required increasing M0+'s private SRAM allocation from 12 to 16 KiB and updating both linkers.

The current shared batch occupies 15,684 bytes, including sample buffers, coefficient plans, and test guards; this is not all scheduler overhead. General buffers and dependency lifetimes/safe reuse still need to be carefully designed. We also need to distinguish queue/wake costs, differences in core processing speeds, and contention for shared-memory bandwidth. Current representative traces show M4 finishing and waiting while a longer M0+ job remains executing. The results do not yet isolate every cause of slowdown, so we will test whether assigning jobs based on core-specific execution costs improves overall completion time.

Poster Session Plan

We plan to show the core/IPC/queue architecture, an execution timeline, and graphs of makespan and speedup across policies and job granularity. We will distinguish fixed-clock gains from gains over the strongest sequential reference, show slowdowns as well as wins, and account for runtime memory. We may also do a small live board demonstration with selected tests, but measured evaluation is the primary deliverable.
