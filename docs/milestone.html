Progress So Far

Since the proposal, we have brought up the dual-core PSoC 6, implemented integer FIR filtering with runtime-supplied coefficients, and profiled scalar and DSP/unrolled kernels. A FIR job filters an independent block with zero initial history; its tap count is the number of coefficients used per output. Infineon supplies startup, timer, and IPC drivers. The filtering kernels, job ownership protocol, and batch execution are project code.

We implemented a single-job cross-core handoff and a naive concurrent baseline. Both cores claim the next unclaimed job, release the hardware lock, and compute independently; M4 does useful work while M0+ runs. Full-output checks, completion counts, guards, and separate timing traces validate execution. The runtime supports up to 32 preloaded FIR jobs in 16 KiB of shared storage. Threshold operations, general enqueueing, dependencies, profiled static assignment, and work stealing remain planned.

Preliminary Results

Experimental Setup

With Arm GCC 14.2.1 (-O2), we measure 31 trials per workload, mode, and clock setting after three warmups. Scalar and DSP/unrolled variants are tested on each core; choices are fixed before parallel trials. The assignment rule itself uses no cost estimates. A common hardware TCPWM counter measures elapsed time using its configured frequency. On this board, M4 at 150 MHz requires M0+ and peripherals at 75 MHz; both cores can instead run at 100 MHz.1

The M4-only reference makes direct filter calls over the same shared buffers, without queue locks or worker wakeup. Parallel timing includes ready-list initialization, publication, IPC wakeup, claiming, execution, and completion waiting. Input/plan preparation and correctness checks are outside both timers. Per-job timestamps are enabled only in separate diagnostic batches.

Across 25 workloads, greedy beat the fastest tested M4-only configuration in 2 cases; the best median speedup was about 1.10×. At a fixed 100/100 MHz, it beat M4-only at 100 MHz in 19 cases, but those gains must not be presented as beating the faster 150 MHz sequential reference. Separate traces confirmed kernel overlap in all 50 traced batches. Across both accepted clock sweeps, 8560 batches and 139,668 job executions passed checks, including warmups and calibration. The earlier single-slot NOOP handoff measured about 5.88 μs round trip at 150/75 MHz.2

Challenges and Remaining Unknowns

Initial bring-up required UART-path diagnosis and a TX/RX jumper workaround, as recorded in our earlier project notes. Our current measurements use KitProg debugger extraction after execution, so timing does not depend on serial output. Earlier large-block tests also required increasing M0+’s private SRAM allocation from 12 to 16 KiB and updating both linkers.

The current shared batch occupies 15,684 bytes, including sample buffers, coefficient plans, and test guards; this is not all scheduler overhead. General buffers and dependency lifetimes still need careful design. We also need to separate queue/wake costs, kernel asymmetry, and concurrent memory contention. Representative traces show M4 finishing while a longer M0+ job remains. The results do not yet isolate every cause of slowdown; we will test whether core-specific execution costs improve placement. We plan to ask staff whether the revised independent-job policy comparison plus a small dependency graph is an appropriate remaining scope.
